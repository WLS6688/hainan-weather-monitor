# 海南天气预警监控 · GitHub Actions

这套方案部署到 GitHub Actions，**无需电脑开机、无需 WorkBuddy 常开**，由云端定时运行。

## 监控范围与规则

- **监控类型（5 类）**：**台风**（含热带风暴/强热带风暴/热带气旋/热带低压等全部强度）、**暴雨**、**大风**、**雷电**、**地质灾害**
  > 曾纳入后又移除的四类：洪水、山洪（与暴雨预警高度重复）、风暴潮、海浪（均属海上，澄迈陆地场景用不上）——这四类既不实时推送也不进日报
- **监控区域**：直查 **澄迈（469023）** 与 **海口（460100）** 两地的预警，另抓 **海南省** 省级预警兜底（省级预警中提到澄迈/海口时同样推送）
- **天气日报**：每天 **07:30** 推送「澄迈预警日报」（08:30 冗余触发一次，靠日期去重）；若这两次定时都被 GitHub 丢弃，08:00 之后每一轮轮询都会补发，当天只发一次
- **即时预警推送触发**：上述预警影响 **澄迈或海口（陆上）** 时，按等级分级推送
  - **多条合并**：一次轮询内无论有几条预警，最多只占 **1 条 `markdown` 合并详情卡 + 1 条 `text` 提醒**，不会逐条刷屏
  - **是否 `@all` 不再"红橙一律"**：改由下面的《全员提醒强度分级》决定（红色首现/升级必 `@`，橙色受冷却与限流约束，橙色持续提醒不 `@`）
  - **蓝色 / 黄色 / 海上预警**：不实时推送，仅在每日报告中展示
  - 同一条预警按**内容指纹**去重：正文没有实质变化就不再重复推送；红色 / 橙色持续生效且内容未变时，每 120 分钟才会再温和提醒一次
- **变化通知（什么会推、什么不会）**：

  | 情形 | 是否推送 |
  |------|---------|
  | 预警等级**升降**（橙→红、橙→黄…） | ✅ 推送（升级走分级推送，降级推一条「预警降级」且不 `@`） |
  | 正文**实质变化**（风力加大、雨量上调、影响时段/范围变化） | ✅ 推送 |
  | 官方"**继续发布**"、内容与上次相同（仅发布时间不同） | ❌ 不推（避免每十几分钟刷屏） |
  | 预警**解除**（仅陆地、且曾推送过） | ✅ 推一条「预警解除」 |
  | 台风预报路径**首次**进入海南影响范围 | ✅ 推卡片 + 路径图；逼近（≤48h）时另补一条 `text` `@all` |
  | 台风**强度升级 ≥1 级** 或 **预计进入时间提前 ≥6 小时** | ✅ 补推一条升级提示，并 `@all` |
- **去重键**：用「发布机构 + 灾种」作稳定键（而非官方 id）。官方 id 内含**发布时刻**，每次"继续发布"都会换 id；若直接用 id，会把"继续发布"误判成"解除 + 新预警"，导致群里反复出现"预警解除"和重复 `@`
- **时间基准**：中央气象台台风接口返回的是**世界时（UTC）**，展示时已统一换算为**北京时**
- **解析兜底**：若官方标题格式异常导致正则无法解析类型/等级，则改用关键词（暴雨/大风/雷电/洪水/山洪/地质灾害/风暴潮/海浪… 及 蓝黄橙红白）兜底识别，避免漏报
- **台风路径图**：当台风逼近/影响海南时，用中央气象台实时路径数据生成 **中文路径图**，作为 `image` 消息发到群里；同时附带 `[实时台风路径·点击查看]` 可点击链接，跳转中央气象台台风网
- **影响判断**：预警提到具体城市→影响该城；全省/全岛→影响澄迈/海口；**其他市县自行发布的预警一律不纳入**（省级接口会返回全省各市县预警，若全量收录，每日报告会被几十条无关预警淹没）
- **海上 / 陆地判定**：以预警**信号名**是否含「海面 / 海上 / 琼州海峡 / 附近海域」等为准。**不用正文判定**——正文里"南海热带低压"这类天气系统表述会把陆地预警误判成海上预警而漏推

## 全员提醒强度分级（谁会被 @ 全体）

企业微信的 **`@all` 只有 text 消息支持**，markdown 卡片不支持。所以早期版本有个矛盾：台风通道全程只发 markdown，
「台风逼近/已进入」这种最该叫醒人的场景**根本 `@` 不到人**；而红/橙预警的持续提醒又一律 `@all`，
一场台风持续 48 小时就是 24 次全员 `@`，人被叫麻木后反而会错过真正重要的那条。

现在的做法是把「发不发内容」和「打不打断全员」拆成两件事，分成三级：

| 级别 | 适用事件 | 是否 @ 全体 | 受限约束 |
|------|---------|------------|---------|
| **L3** 立即全员 | 红色预警首现 / 升级为红色 · 台风已进入影响范围 · 台风强度升级 · 台风进入时间提前 | **必 `@`** | 无视冷却、无视夜间静默、不受每日熔断限制（真紧急情况不该被规则挡住） |
| **L2** 缓一缓再全员 | 橙色预警首现 / 内容变动 · 台风逼近（≤48 小时）· 红色持续提醒 | 视情况 `@` | 同级冷却 60 分钟 · 同一预警 12 小时内只 `@` 一次 · 夜间静默 · 每日 8 次熔断 |
| **L1** 静默卡片 | 橙色持续提醒 · 预警降级 · 预警解除 · 每日日报 · 热带扰动 · 台风远距离趋向（>48h） | 不 `@` | 只发 markdown 卡片，不发 text（text 的全部价值就在于它能 `@` 人） |

**被限流时不是不发，而是降级为卡片**，并在卡片尾部写明未 `@` 的原因，例如：

> （距上次全员提醒不足 60 分钟，本次未 @ 全体）
> （夜间静默，本次未 @ 全体）

省下的是敲门次数，不是信息量——卡片照常在群里，早上翻记录一条不少。

### 可调参数（都在 `monitor.py` 顶部配置区）

| 常量 | 当前值 | 含义 |
|------|-------|------|
| `ATALL_COOLDOWN` | `3600` | L2 同级 `@all` 冷却秒数（60 分钟） |
| `ATALL_DAY_LIMIT` | `8` | L2 每日 `@all` 熔断上限（次）；L3 不受此限 |
| `REPUSH_ATALL_MIN` | `12 * 3600` | 同一条预警的持续提醒，`@all` 最小间隔（12 小时） |
| `QUIET_HOURS` | `(23, 0, 6, 30)` | 夜间静默段：北京时间 23:00 – 次日 06:30 |

### 夜间值班点名（可选）

夜间静默期内若仍希望有人知道，可以配一份值班名单——本该 `@all` 的 L2 事件会改为**只点这几个人的名**：

1. 取企业微信 **userid**：管理后台 → 通讯录 → 点开成员 →「账号」栏（形如 `ZhangSan`，不是昵称也不是姓名）
2. 仓库 `Settings` → `Secrets and variables` → `Actions` → `New repository secret`
   - Name：`NIGHT_DUTY_USERS`
   - Value：`ZhangSan,LiSi`（英文逗号分隔，不要空格）
3. 保存即生效，**无需改代码、无需重新部署**

> 手机号兜底：`NIGHT_DUTY_MOBILES`（填 `138xxxxxxxx,139xxxxxxxx`），仅在 userid 名单为空时生效。
> 本仓库是公开的，标识信息一律走 Secret，**不要写进代码**。名单为空时系统保持纯夜间静默（红色与台风已进入仍无视静默 `@all`）。

## 一、你需要准备

- 一个 GitHub 账号（免费注册：https://github.com ）
- 企业微信群机器人 webhook（就是之前那个 `qyapi...webhook/send?key=...`）

## 二、部署步骤（全程 5 分钟）

### 第 1 步：创建 GitHub 仓库

1. 登录 GitHub，点右上角 `+` → `New repository`
2. 仓库名随意，如 `hainan-weather-monitor`
3. 选 **Public（公开）** 或 **Private** 均可；本仓库已切为 Public 以使用无限免费 Actions 分钟数，webhook key 不写在代码里，只放在 GitHub Secret 中
4. 不要勾选任何初始化选项（README 等），点 `Create repository`

### 第 2 步：上传代码

本地打开终端，进入本目录（`.workbuddy/github-actions`），执行：

```bash
git init
git add .
git commit -m "init weather monitor"
git branch -M main
git remote add origin https://github.com/你的用户名/hainan-weather-monitor.git
git push -u origin main
```

> 把 `你的用户名` 换成你的 GitHub 用户名。

### 第 3 步：配置 webhook 密钥

1. 打开你的仓库页面 → `Settings` → `Secrets and variables` → `Actions`
2. 点 `New repository secret`
3. Name 填：`WECHAT_WEBHOOK`（与 `.github/workflows/monitor.yml` 中 `secrets.WECHAT_WEBHOOK` 对应）
4. Value 填你的 webhook：`https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=6cbed4be-c980-41cb-8e1b-625f4ea8e017`
5. 点 `Add secret`

### 第 4 步：启用工作流

1. 仓库页面 → `Actions` 标签
2. 如果提示 `I understand my workflows, go ahead and enable them`，点它启用
3. 找到 `海南天气预警监控` 工作流

### 第 5 步：测试

在 `Actions` 页点工作流右侧的 `Run workflow` → `Run workflow`，手动触发一次，验证能收到群消息。

## 三、定时规则说明

工作流里的 cron 用的是 **UTC 时间**（北京时间 - 8 小时）：

| 任务 | 北京时间 | UTC cron |
|------|---------|----------|
| 每日预警日报 | 07:30（08:30 冗余一次） | `30 23 * * *` / `30 0 * * *` |
| 预警轮询 | 每 10 分钟（:03/:13/:23/:33/:43/:53） | `3,13,23,33,43,53 * * * *` |
| 热带扰动物理监测 | 每 1 小时（在轮询内节流） | 无需单独 cron，代码内 3600s 限频 |

> 所有 cron 都**刻意避开整点**：GitHub Actions 在整点负载最高，schedule 事件会被延迟数小时甚至直接丢弃
>（本项目实测出现过单次延迟 5 小时、以及连续 2 小时零执行）。日报另有兜底：08:00 之后只要当天还没发过，
> 每一轮轮询都会补发一次。

> 说明：热带扰动监测需扫描 6 个近海点（Open-Meteo），按 1 小时限频后约 **144 次/天**外部调用；预警轮询本身复用同一批接口，不再额外增加请求。

## 四、常见问题

**Q：GitHub Actions 免费吗？会扣费 / 消耗积分吗？**
不扣费、不消耗积分。本仓库已设为 **Public（公开）**，公开仓库的 Actions **分钟数无限且完全免费**。
（私有仓库才有额度限制：免费账号 2000 分钟/月。按每 10 分钟一次轮询 ≈ 145 次/天、每次约 1.5–2 分钟计算，月耗约 7500–8700 分钟，私有仓库早就超额——这正是当初改成 Public 的原因。）

**Q：运行这个需要多少内存 / 磁盘？**
GitHub 托管的 `ubuntu-latest` 运行器规格为 **4 vCPU / 16 GB 内存 / 14 GB SSD**，远超需求：
脚本本身常驻内存只有几十 MB，仅生成台风路径图那一刻 matplotlib 会占用约 200–400 MB。**内存从来不是瓶颈**，无需为此担心。

**Q：我的电脑关机了，还能跑吗？**
能。任务跑在 **GitHub 的云端服务器**上，与你本地电脑是否开机、是否联网完全无关。你关机、断网、出差都不会影响推送。
（唯一例外：如果你在本地手动执行 `--mode poll` / `--mode daily` 调试，那当然需要开机。）

**Q：定时任务会准时吗？会自己停掉吗？**
GitHub Actions 的 schedule 可能有几分钟到十几分钟的延迟（尤其在高峰），但基本可靠。若需严格准点，可改用付费方案或自建服务器。
另外 GitHub 有条规则：**仓库 60 天无任何活动会自动停用定时任务**。本项目每轮都会把 `state.json` 提交回仓库，本身就是活动，因此不会触发停用。

**Q：换群怎么办？**
只需更新仓库里的 Secret `WECHAT_WEBHOOK` 的值即可，代码不用动。

**Q：怎么停止？**
仓库 `Settings` → `Actions` → `General` → 关闭 Actions，或删除仓库。

## 五、推送历史与溯源

每一条推送都会被记录并随仓库提交，可随时回查「什么时候、推了什么、什么等级、是否附图」：

| 文件 | 说明 |
|------|------|
| `data/push_log.jsonl` | 主审计日志，逐行 JSON（可程序化统计） |
| `data/archive/YYYY-MM.md` | 月度可读归档，逐月翻查方便 |
| `data/history.csv` / `history.md` | 导出文件，用下面的命令生成 |

导出（本地运行）：

```bash
python3 monitor.py --mode export              # 生成 data/history.csv（Excel 可直接打开）
python3 monitor.py --mode export --format md  # 生成 data/history.md
```

> 因为日志随仓库提交，你也可以直接在 GitHub 仓库里点开 `data/` 查看，或用 Git 历史追溯任意时间点的记录。详见 `data/README.md`。
